# Sparse CDC and crash trial

Run [EXP-022](../../../docs/experiments/EXP-022-sparse-feedback.md) on the reviewed stock pin. The launcher reuses the gate's isolated publisher and consumer setup, WAL sampler, exact parity adapter, same-slot recovery checks and guarded teardown.

## Stage and run

Use the [existing staging recipe](../cdc-baseline/README.md#stage) with two fresh, disconnected guest overlays. Hold the host's exclusive `/tmp/cdc-lab-vm-runtime.lock` until each guest powers off. Use the current checkout for the archived revision, read-only media and pinned archives. Verify its manifest, exact revision and actual overlay identity as in the [gate runbook](../../../docs/cdc-gate.md#schedule-and-stage).

1. In one overlay run `make test-cdc MEDIA=/mnt/stage` to reproduce the original paired control, including exact S00–S05 on both projects. The stock image is expected to return a failed paired subgate with two retention failures. A fatal setup or teardown error does not reproduce the control.
2. In the next overlay run `bash tests/integration/cdc-sparse/run.sh /mnt/stage`. This uses another fresh project and held serial onboarding. It verifies exact S00, S01 insert and S02 update. Each of three epochs commits one value-preserving update each to order 10, item 101 and payment 301, switches one 16 MiB segment and checkpoints. The customer mapping remains idle. It holds source workload writes for 20 seconds and checks exact S02, then repeats one epoch. It commits the real S03 deletion, samples for queued work with exact old target, SIGKILLs the consumer, and reads its persisted state before restarting the worker. It verifies exact recovered S03, S04 and S05 on the original group and slot.
3. Export the run directory in redacted form and confirm `experiment_exit=0 cleanup_exit=0` in `run.txt`. Read `sparse.json`, the timing and full position samples in `timeline.jsonl`, exact all-table and report exports, cgroups and disk in `resources.txt`, and the allow-listed recovery logs. Group and per-table positions, producer brackets and publisher feedback belong to separate observations. The source insert position before the delete is a conservative lower bound, not its decoded COMMIT or END LSN.

For the separate crash-window control, run `bash tests/integration/cdc-sparse/run.sh /mnt/stage sparse-delayed-flush` in another fresh overlay. It sets and checks the supported flush interval at 12 seconds before any mapping is created so the just-flushed item queue has a longer cooldown before the S03 delete. Document its distinct effective configuration and use the same WAL and time ceilings.

The sparse stage is limited to 150 seconds, the full workload to 480 seconds plus the existing 60-second teardown allowance, per-epoch apply polling to 18 seconds and per-checkpoint parity polling to 60 seconds. There are four switches maximum, with a 17 MiB preflight allowance each. Stop before projected retained span reaches 64 MiB or projected headroom reaches 64 MiB. Alert at observed headroom at or below 96 MiB. Check resources before generating WAL and after each epoch. The existing 128 MiB slot setting, less than 256 MiB physically allocated publisher WAL, less than 512 MiB per volume, 1 GiB free disk floor and all cgroup limits remain in force. The trial writes only these explicit transactions and the fixed fixture scenarios.

Successful command execution means the bounded measurement and cleanup ran. Stock feedback should remain fixed as retained WAL grows. A candidate would need feedback covering each fully durable epoch, a steady physical WAL budget and reclaimed/recycled retention under repeated epochs, exact parity and the witnessed pre-apply restart. The short bounded stock run cannot establish a steady-state recovery guarantee. If the pre-worker target has exact S03, the pre-apply window was missed even if an earlier read still had item 102.

If WAL is lost, stop writes, preserve the slot state, last exact checkpoint and reconnect logs. Follow the separately tested [guarded loss procedure](../../../docs/experiments/EXP-018-cdc-recovery.md#retention-crossing-reconnect-failure-and-clean-resnapshot) only for verified disposable identities. Treat the resulting catalog as a fresh snapshot of current source state. The retired stream and its history are unavailable through that procedure.
