# Component compatibility and candidate versions

Public sources and registries accessed **2026-11-24** for [ticket 0.1 (GitHub #6)](https://github.com/TiaanViviers/cdc-lakehouse-lab/issues/6). **Documented** means an upstream manual or pinned source describes the behavior. **Observed** refers to release, registry, or CI metadata inspected during this review. **Candidate** means a version selected for a future check. This matrix records documentation and artifact inspection. The [Phase 1 closeout](phase-1-closeout.md) records observed stock source behavior. As of 2026-11-26 remote CDC and the downstream integrations remain untested. [Phase 2 candidate inspection](experiments/EXP-010-phase-2-candidate-review.md)

## Risk and decision summary

**First runtime uncertainty (Phase 2, R01).** Can DuckPipe's available PG18 image register a remote stock PG16 source and maintain a DuckLake table through initial copy and committed changes? Start with one small source table and the bundled sink on disposable local storage. Capture the actual PostgreSQL and extension versions, preload settings and catalog format before registering the table. Compare exact keys and values before and after an insert, an update and a delete. Inspect the source publication and slot and the DuckPipe status separately. The pinned API creates a persistent slot before creating the publication, then adds each table and sets its replica identity to FULL. PostgreSQL requires database CREATE and ownership rights on the registered tables for these operations. Verify scoped onboarding, temporary-slot usage and cleanup on a disposable publisher. [Pinned API](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-pg/src/api.rs) [Remote sync guide at the candidate commit](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/doc/REMOTE_SYNC.md) · [PostgreSQL 16 replication security](https://www.postgresql.org/docs/16/logical-replication-security.html)

**Decision for the experiment.** Use the digest-pinned DuckPipe CI artifact for the isolated smoke test. The registry has a May artifact based on PG18.4, while the same commit's November pipeline failed during Docker Hub authentication and skipped image publication. If the image fails to start or register the source, preserve the failing step and test a pinned rebuild on PG18.7 using the original DuckPipe dependency revision. A PG17 consumer is a second documented host candidate if host-specific behavior is implicated. Keep the publisher on PG16 in either case. A switch to the separate DuckPipe daemon or another CDC mechanism would require a proposed ADR with the runtime evidence. [Successful May build](https://github.com/relytcloud/pg_duckpipe/actions/runs/26499999069) · [Failed November build](https://github.com/relytcloud/pg_duckpipe/actions/runs/45203850543)

**Smoke-test image authentication.** On initial setup, the pinned image's init script appends `host all all 127.0.0.1/32 trust` and `host all all ::1/128 trust` to `pg_hba.conf`. A matching rule permits a loopback TCP connection without a password. Use this image only in a disposable environment on an isolated Docker network, with PostgreSQL ports unpublished and untrusted processes excluded, including from the consumer's network namespace. After startup and before registering the source, run `SHOW hba_file` on the consumer and inspect `pg_hba_file_rules` for rule order and parse errors. Confirm the expected authentication with fresh loopback and peer-container connections because the view reads the file on disk. Keep these loopback trust rules confined to this experiment. [Pinned init script](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/docker/init.d/0002-localhost-trust.sh) · [PostgreSQL HBA rule matching](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html) · [PostgreSQL HBA inspection view](https://www.postgresql.org/docs/18/view-pg-hba-file-rules.html)

**Largest downstream risk (Phases 3–5).** The Dockerfile's DuckPipe dependency expects DuckLake catalog format **0.4**. The standalone `pg_ducklake` v1.0.3 build vendors a DuckLake implementation targeting **1.0**, and current DuckDB 2.0 clients require migration before using pre-1.0 catalogs. If the smoke test confirms 0.4, first try a format-matched DuckDB 1.5.1 read on the actual catalog with migration disabled. That can establish a read baseline for Phase 3. Phase 4's native Windmill runner and Phase 5's FDW still need a shared compatible format. Compare a newer, jointly tested writer build with a format-matched worker or serving build if needed. Any migration investigation should use a disposable copy and verify that the live writer can still use its original catalog. [0.4 initializer at the DuckPipe dependency pin](https://github.com/relytcloud/pg_ducklake/blob/20d799e673639fb0c36a3b31db413e45057a10ed/third_party/ducklake/src/storage/ducklake_initializer.cpp) · [1.0 initializer at the serving build's submodule pin](https://github.com/duckdb/ducklake/blob/93cc490d9b5554f6fd5322dbef23f41d4fa91bb8/src/storage/ducklake_initializer.cpp) · [DuckLake migration rules](https://ducklake.select/docs/stable/duckdb/migrations/upgrading_to_ducklake_1_1)

**S3 and orchestration.** SeaweedFS 4.55 Community is the first local S3 candidate because it has a versioned public image and documents the required API surface. Phase 3 needs signed path-style requests, range reads, listings, multipart writes and cross-bucket denial on the actual clients. Phase 6 also needs verified artifact immutability or versioned reads and checksums. Use an explicit Flow and a tested readiness check as Phase 4's baseline. Compare the alpha Pipeline on the same lake and test an external DuckPipe write separately. Community Pipeline tests can fail after publication, so a successful Flow/Pipeline run and the visibility of correct Gold data need separate evidence. [SeaweedFS 4.55](https://github.com/seaweedfs/seaweedfs/tree/4.55) · [DuckDB S3 requirements](https://duckdb.org/docs/current/core_extensions/httpfs/s3api) · [Windmill Pipelines](https://www.windmill.dev/docs/core_concepts/pipelines)
