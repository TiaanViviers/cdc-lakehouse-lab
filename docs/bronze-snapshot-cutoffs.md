# Transaction-completion watermarks and Bronze snapshots

**R13 investigation · 2026-11-27 · Static finding and research proposal.** No supported source-transaction-completion watermark or live snapshot barrier was found in the pinned DuckPipe PostgreSQL extension. The exposed telemetry and worker state cannot safely select a transaction-consistent snapshot while source writes continue. EXP-019 supplies a direct counterexample for selecting latest. A connector change or a materially different ingestion contract is the credible direction for a general solution. Keep the held, exactly verified checkpoint for Phase 3 and the initial Windmill lab baseline. [Pinned public SQL API](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-pg/src/api.rs) · [Observed partial snapshots](experiments/EXP-019-cdc-visibility.md#s04-commit-and-the-exp-017-counterexample)

## Positions and guarantees

| Boundary | Verified semantics and current limit |
| --- | --- |
| Source commit and decoded progress | PG16 pgoutput exposes BEGIN final LSN/XID and COMMIT commit/end LSNs. The selected transport uses protocol 1, so decoded rows from a committed transaction can arrive before its COMMIT message is processed by DuckPipe. The service parses and discards BEGIN fields and on COMMIT updates the group's `pending_lsn` to the decoded end LSN. It routes row mutations into table queues as it receives their messages. `pending_lsn` is a decoded frontier used to drive CATCHUP → STREAMING. The code maintains no per-source-transaction manifest of table effects attached to a committed lake version. Phase 2's ordinary publisher samples are upper WAL brackets around commit. | Transport acknowledgement and restart | DuckPipe computes a minimum of the tracked table positions, seeds positions from persisted state and sends that value as feedback. Under the locked transport one position populates write, flush and apply feedback. Publisher `confirmed_flush_lsn` records logical receipt. `restart_lsn` determines which WAL may still be needed and can lag. The persisted group position helps resume. PG16 can start at the later of request and slot-confirmed positions and can resend after a publisher crash. These fields carry no snapshot ID or complete source prefix. The pinned SQL API exposes group lifecycle, worker start/stop, resync, configuration and status. No public call establishes a coordinated live flush at a requested source COMMIT. The core defines `drain_and_wait_all` as an internal drain helper described for shutdown, with per-thread waits and a timeout. Source search found no call site in this revision. DDL/TRUNCATE barriers order work on one table. A valid live boundary also needs proof that all scoped changes before an attributed commit were admitted and that no later effects entered the selected snapshot. ## Why a polling coordinator cannot certify a source prefix

A safe boundary binds a scoped set of relations and source stream identity to a particular committed source prefix and a reproducible retained DuckLake version. At that version, all of the prefix's relevant effects must be represented, and later effects must be excluded or covered by a separately certified later prefix. The relation scope, publisher identity and catalog generation matter across onboarding, resnapshot, failover and schema changes.

Even if a future retention fix makes all table counters progress, a minimum might only establish a lower bound on admitted or applied work under additional invariants. It cannot establish the upper boundary of what is visible. Suppose committed A updates two tables and later B updates two tables. One worker can flush its A and B changes before the other flushes A. The retained sequence may jump from incomplete A with newer B effects to complete A with only part of B. There may be no exact A version to select. When all of B lands, the later version needs its own proof of completeness, including transactions already in flight. A polling coordinator cannot reconstruct that ordering from scalar LSNs, queue depth, clocks, SQL health or object writes. Idle tables freeze the currently tracked minimum, and disabled/error states, snapshot admission and resnapshot can change coverage. A source marker on one table has the same race. Touching all tables, even in one transaction, leaves later work unfenced and the resulting snapshot unattributed. Repeated polling with no visible change is bounded by the sample schedule. [Measured sparse stall](experiments/EXP-020-phase-2-cdc-gate.md#active-retention-and-resource-measurements) · [Per-table worker design](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/README.md)

An independent decoder on a separately authorized, bounded disposable slot could observe transaction order and expected row changes for an experiment. It could test a known fixture against retained versions. It cannot tell which opaque current-state writer batches made each version or force a boundary under continuous writes. Full reconciliation with a source read snapshot may certify a matching finite dataset under a defined coverage contract. It carries source workload and attribution costs and can miss intermediate versions. A general coordinator needs either a writer-supported fence and durable source-to-lake attribution, or application-specific semantics with strict source ownership and immutable, independently verifiable batches. The latter would be a different ingestion contract requiring review. Never consume, acknowledge or advance the active writer slot from an observer.

## Most valuable next research

**Placement.** Record the negative API finding now. In Phase 3 verify retained file-backed reads independently and let a later worker consume a known held cutoff. Keep a continuous-cutoff implementation off the Phase 3 critical path. When the corrected CDC path and the independent reader are known, review a bounded R13 feasibility experiment before any continuously driven Phase 4 publication. Feed proven ordering and failure results into the later integrated resilience study.

**Hypotheses to compare.**

- A transaction-aware writer could preserve source stream epoch and COMMIT identity, track the exact participating mappings, wait for full durable effects, and publish a catalog snapshot representing a contiguous prefix. One design is an ordered, atomic multi-table apply of one or more complete source transactions. Another stages independent work and fences newer effects until a coordinated catalog publication. The source keeps committing while ingestion may briefly buffer later transactions. Bound queues, scratch, backpressure and retention. Provide a durable, crash-safe association between prefix and snapshot, committed atomically with certification or made replayable under an enforced write fence. A background observer may consume this contract once proved.
- An application-managed batch or immutable event contract could supply explicit membership and completeness to a coordinating pipeline without modifying DuckPipe's current-state apply loop. It changes the data contract and may require a separate materialization path. A diagnostic slot, current-state rescan, marker and all-table heartbeat are useful experimental controls that leave the general cutoff unverified.

**Experiment contract.** On a fresh synthetic setup with bounded work, capture source cluster/stream identity and committed transaction identities/end positions from attributable decoding, independently recorded expected effects for every prefix, mapping and writer generation, durable apply results, catalog identity and numeric version. Require a live source writer to continue committing during selection. Force delayed tables, both orders of completion where relevant, idle and changing membership or fail closed on membership change, rollback and a later disjoint commit, overlapping A/B with partial newer work, repeated mutations to the same key, and delete/reinsert. Force bounded crashes before durable apply, after durable apply and before certification, after certification but before feedback, and during replay. Include an acknowledgement stall and an invalidated-slot/new-generation case. Prove that no incomplete or unknowable view is certified, that safe forward progress resumes within declared bounds, and that the selected ID is read exactly in a fresh independent DuckDB process before and after later versions and recreation. Protect that version and its referenced files for the consumer's retention window. If a supported experiment cannot establish those guarantees, record a reproducible negative or bounded inconclusive result and keep automated publication blocked for continuous-source consistency.

A future Windmill run would take a catalog identity/generation, certified retained version and source cutoff identity as immutable input. It should fail closed when that input is missing, expired or unsupported, and record the same input across retries and published output lineage. The demonstrated lab contract remains a held source checkpoint with independent exact parity, including both reports, followed by explicit version reads through a compatible client.
