# Phase-level correctness and observability protocol

Ticket 0.4 ([GitHub #9](https://github.com/TiaanViviers/cdc-lakehouse-lab/issues/9)) defines planned verification for the [roadmap](roadmap.md) and [PoC requirements](poc-specification.md). Use the [v1, seed 42 synthetic workload](synthetic-workload.md) and the [compatibility matrix](compatibility-matrix.md) to prepare each run. The checkpoints and outcomes below are expectations. Runtime behavior and candidate compatibility still require experiments.

Upstream references were reviewed on 2026-11-24. PostgreSQL examples target major 16, DuckLake examples target format 0.4, and DuckPipe status is referenced at the candidate source revision. Record actual runtime versions and validate the interfaces before using the examples.

## Acceptance and evidence

- [ ] Before running, record the hypothesis, fixture checkpoint, expected rows and invariants, exact commands, and pass/fail conditions. Choose numeric polling, convergence and recovery deadlines and resource ceilings appropriate to the pinned local setup. Record them before injecting faults or collecting timings. Later runs use the same limits or explain the change.
- [ ] Record the observed result for each applicable phase check and link the evidence. A check passes when it meets its declared tolerances and deadline. Record a mismatch or missed deadline as a failed check, an unavailable dependency or interface as blocked, and insufficient evidence as inconclusive. Mark a hypothesis disproven only if the evidence contradicts it. Rerun a corrected experiment under a fresh run ID. Use the [experiment template](experiments/TEMPLATE.md) and update the [research register](research-questions.md) with the supported conclusion and its limits.
- [ ] Ensure a reviewer can reproduce the run from the recorded commit, service roles, image digests, PostgreSQL and extension versions, catalog format, tooling versions, redacted configuration, fixture version/seed and commands. Point to the exact output or query for every gate claimed. Preserve evidence of failed and timed-out attempts alongside the successful runs.

Use a run ID like `20261124T130000Z-p02-01` (UTC start, two-digit phase, sequence within that start time). Keep the fixture scenario IDs `S00`–`S06` intact. Use separate fields for variant (e.g. `rollback`, `consumer-restart`), checkpoint (e.g. `S05/A`, `S05/B`) and attempt number. For S06 keep `S06` as the step and `S04` as the replayed idempotency key. Record actual UTC observation times separately from the fixture's fixed business timestamps.

Use one small trace table or CSV per run. Each entry carries run/scenario/attempt, UTC time, service or database role, evidence reference and the boundary identifiers below. Correlate by keys and recorded input/output IDs. Timestamps help locate evidence. LSNs are comparable only within the same source WAL history, and snapshot IDs only within the same catalog.

Keep raw output outside version control, for example in `/tmp/cdc-lab-evidence/<run-id>/` while running. Move needed artifacts to durable, approved storage before cleanup. Put the reviewed summary, exact redacted commands, small synthetic result/diff excerpts and durable artifact references in `docs/experiments/EXP-NNN-*.md` and link it from the PR. Label expected and observed output separately. Remove credentials, connection strings, signed URLs, tokens and private system details before sharing. Do not commit generated databases, object payloads or full logs.

## What to capture at each boundary

| Evidence class | Boundary and identifiers to record | Claim supported by the evidence |
| --- | --- | --- |
| Operational commitment | Source database, scenario or request/batch key, table and PK, transaction ID where exposed, commit outcome/time, and source rows from a separate session. Include the source-side receipt where applicable. | Source visibility and, with a receipt in the same transaction, which operation committed. An application timeout leaves the outcome ambiguous until reconciled. |
| Replication metadata | Source publication, database/slot, WAL samples and any decoded commit/end LSN. Consumer group, table status, checkpoint/ack fields if exposed, and bounded log window. | Which relations are selected and how the consumer progressed. These signals alone leave target values and cross-table visibility unverified. |
| Lake metadata and storage | Catalog format and ID, Bronze or output snapshot ID, table, data/delete-file references and local S3 bucket/object key, size and version if available. | What the catalog associates with that snapshot and which objects the storage API can see. A listing alone leaves the snapshot's logical rows unverified. |
| Data correctness | Independent read-only DuckDB connection to that catalog and its objects. Record pinned snapshot, exact SQL, expected and actual keyed rows, duplicates and differences. | Which values and deletions a reader can see at the named snapshot. |
| Job execution | Windmill parent and step job IDs, trigger, attempt, worker, code revision, start/end, status and error. Record input cutoff and the output snapshots each attempt committed or exposed. | Which code ran with which declared input. Independently check the output even when a job succeeded or failed. |
| Served data | Query endpoint and role, SQL and parameters, client/driver, Gold snapshot or controlled stable window, returned rows or SQL error. | What an external client actually saw. Compare to independent DuckDB at the same Gold version and confirm real object reads. |
| Durable request and prepared artifact | Request DB ID, dedupe key and payload identity, state/attempts, optional Gold input snapshot, and operational bucket key/version, byte checksum and expected batch rows. | The request persisted and the candidate file can be retrieved and validated. Completion requires source receipts and committed business rows. |

## Reusable checks

### Row parity and deletion

1. Run one scenario at a time for the baseline. Keep later fixture writes paused until the current checkpoint is captured and compared. Export all expected fixture rows from the specification and all actual source rows in a single read-only PostgreSQL `REPEATABLE READ` transaction started after the checkpoint commit. Compare the source to the fixture before using it as the Bronze oracle. [PostgreSQL 16 transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html)
2. Compare both directions using table + PK and every specified column. Sort by numeric PK, normalize timestamps to UTC at the declared precision and amounts to integer cents, and preserve types and nulls. Record duplicate keys separately before a keyed comparison, then report missing keys, extra keys and per-column mismatches using null-safe equality. The pass condition is zero of each. Verify the comparison detects a wrong value even when row counts agree.
3. Capture S00 before CDC registration for initial-copy parity. At S01 verify item 102 has the specified values and timestamps. At S02 verify item 101 quantity 3, original `created_at` and updated T02. At S03 verify item 102 is absent from the logical source and Bronze results and every other scoped row still matches. A later match alone could hide an insert and delete that were both missed. A retained earlier snapshot may still show item 102. Physical removal of a backing file is a separate maintenance concern.
4. For Silver and each Gold output, declare the grain, exact expected keys/values and invariants independently of the production transformation SQL. Compare full deterministic outputs, including groups with zero values where specified. Use both customer rows in the fixture Gold Reporting oracle. Payment joins must leave item totals unmultiplied.

### WAL progress and convergence

Start with an idle fixture and sample before mutation, after source commit, during consumer catch-up and when the independent read matches. For each source sample, use an allow-listed projection such as the PostgreSQL 16 query below. Replace the slot placeholder with the recorded lab slot. At setup check `wal_level` and `max_slot_wal_keep_size`, record published tables and filters from `pg_publication_tables`, and confirm the published operations and replica identities. [PostgreSQL 16 publication semantics](https://www.postgresql.org/docs/16/logical-replication-publication.html)

```sql
WITH sample AS (SELECT clock_timestamp() AS sampled_at, pg_current_wal_insert_lsn() AS source_lsn)
SELECT sampled_at, slot_name, database, plugin, active,
       source_lsn, restart_lsn, confirmed_flush_lsn, wal_status, safe_wal_size,
       pg_wal_lsn_diff(source_lsn, restart_lsn) AS retention_span_bytes,
       pg_wal_lsn_diff(source_lsn, confirmed_flush_lsn) AS unconfirmed_span_bytes
FROM sample CROSS JOIN pg_replication_slots
WHERE slot_type = 'logical' AND slot_name = '<lab-slot>';
```

- **Documented.** `restart_lsn` is the oldest WAL location potentially still needed by the slot. `confirmed_flush_lsn` is the position the logical consumer confirmed receiving. The protocol has distinct feedback positions and logical commit/end LSNs. A sampled WAL insertion point brackets activity and can include unrelated WAL. Byte deltas approximate cluster WAL spans and can be null; they do not measure row backlog, actual disk use or latency. Slot position can rewind after a source crash and changes may be delivered again. [PostgreSQL 16 slot view](https://www.postgresql.org/docs/16/view-pg-replication-slots.html) · [WAL functions](https://www.postgresql.org/docs/16/functions-admin.html) · [Replication feedback](https://www.postgresql.org/docs/16/protocol-replication.html) · [Logical messages](https://www.postgresql.org/docs/16/protocol-logicalrep-message-formats.html) · [Logical decoding concepts](https://www.postgresql.org/docs/16/logicaldecoding-explanation.html)
- **Planned.** On the candidate consumer start with `SELECT source_table, state, rows_synced FROM duckpipe.status();`. Capture group/slot mapping and any checkpoint or LSN fields with meanings verified for that build. If the transaction's decoded commit/end LSN is exposed, correlate it by transaction or fixture keys and compare to the relevant acknowledged position. Otherwise preserve ordered source samples around the commit and report the correlation at checkpoint level. Inspect the live slot without consuming from it. [Pinned DuckPipe status and per-table flush design](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/README.md)
- **Open (R04/R05).** Determine what receipt, apply, durable checkpoint and acknowledgement mean for the selected DuckPipe build by pairing samples with snapshot reads and restart/replay evidence. `STREAMING`, a drained queue and advancing acknowledgements are progress signals. The convergence condition is the first independent read of a single named lake snapshot with zero differences across all scoped tables after the hold point. Where a transaction end LSN is available, record whether and when the ack reaches it, separately from data convergence.

For the Phase 2 local baseline, if the simplest sink is only readable through the consumer host, use a separate read-only SQL session for exact sink parity and record the supported read boundary. Independent DuckDB attachment, file-backed verification and retained snapshot reads are Phase 3 requirements. If Phase 2 exposes only per-table reads, limit that evidence to per-table convergence with later fixture writes paused.

**Timing check.** Record UTC times for source commit completion, first observed acknowledgement if attributable, first correct Bronze read, Windmill queue/start/end, verified output publication and first correct served result as applicable. Report elapsed times from one observer's monotonic clock where possible, with poll interval, deadline and last failed/first passing observations. Report missing stages as unobserved or timed out. Fixture timestamps are business data and cannot measure latency. Bounded convergence in this local run makes no claim about an SLA or zero lag under continuous writes. Treat local S3 API behavior and asynchronous source-to-lake convergence as separate measurements. [AWS S3 consistency contract for AWS S3](https://aws.amazon.com/s3/consistency/)

### Stable snapshot and multi-table cutoff

1. On the actual catalog created by DuckPipe, attach from a separate, format-matched DuckDB process with read-only catalog and object access and automatic migration disabled. Record the catalog identity and retained snapshot ID. In the documented 0.4 API use `snapshots()` to discover versions and query all tables with the same `AT (VERSION => …)` or use a snapshot-version attachment. Save the exact SQL for the installed build. An attach error blocks independent verification of that catalog. [DuckLake 0.4 attach options](https://ducklake.select/docs/0.4/duckdb/usage/connecting) · [DuckLake 0.4 time travel](https://ducklake.select/docs/0.4/duckdb/usage/time_travel)
2. Read the same retained snapshot from a fresh connection after a later commit. It must still match its original expected rows, and a newer snapshot must show the intended delta. Match snapshot-visible data and delete-file references to object metadata. For the S3 gate, ensure scoped rows actually reside in referenced Parquet (flush inlined rows through the supported interface if needed). Correlate the query with object reads or demonstrate that a fresh read of those rows fails when access to the referenced objects is removed and recovers when it returns. Listing files or scanning loose Parquet bypasses DuckLake's logical delete/snapshot semantics.
3. **Open (R13).** DuckLake documents a consistent view of its own snapshot. Test whether that view represents a full *source* checkpoint. With S04 held open, query from a separate source session and inspect Bronze. Expect none of the three new keys. In a separate rollback variant, verify absence after CDC applies a later, disjoint committed change whose expected values were recorded before the run. In the commit run, sample intermediate lake snapshots during a bounded apply delay where supported. Query all three keys at each retained version and record whether versions contain none, some, or all. An observed partial version disproves atomic source-to-lake visibility in that run. Seeing only complete versions bounds the claim to the tested schedule and captured versions. Run S05 with both transactions open before either commits, A then B, and capture A-only and A+B cutoffs where observable. A missing intermediate snapshot may reflect coalescing. Record whether B can be seen before A.
4. Start with a controlled readiness rule for transformations: pause later fixture writes, verify full parity at a single Bronze snapshot, and pin that snapshot as the input. Detect partial states and prevent their use for Gold publication; prove the rule under delayed apply before relying on it. A cutoff for continuously changing source data needs separate evidence that all required relations cover the same source transaction boundary. If only the quiescent cutoff is verified, limit downstream claims to it. Wall timestamps, latest reads of different tables and a single slot LSN cannot establish that stronger cutoff.

## End-to-end walkthrough

Use the S03 state as the baseline. Trace S04 and keep S05 paused until the first report check ends. All values below are planned expectations.

1. **Source.** In the source pgAdmin Query Tool session, select the exact order 30, item 301 and payment 302 keys while the writer holds S04 open. Expect none. After commit, start a fresh read transaction. Expect order `(30, 1, O30, paid)`, item `(301, 30, 1, C, 2, 200)`, payment `(302, 30, P302, 400)`, and T04 timestamps for all three. Record the transaction/fixture receipt if available. The commit proves source state only.
2. **CDC.** In the source tab inspect the publication and slot samples. In the separate consumer tab query DuckPipe status and use its local logs to correlate supported checkpoint fields and errors. Label any LSN bracket as a bracket. A healthy consumer and forward ack may coexist with an incomplete lake cutoff.
3. **Lake.** In the catalog tab inspect the retained snapshot and referenced objects. Locate them in the local object-store browser and collect API metadata. In independent DuckDB read all four tables at that version and compare to S04. A visible Parquet file can belong to an older snapshot or represent only one part of the change. Keep any partial version as evidence.
4. **Windmill.** Open the Runs page, locate the Flow/Pipeline by recorded job ID and follow its step attempts. Log the verified Bronze snapshot and Silver/Gold output versions. In independent DuckDB verify Silver and both Gold outputs against their declared oracles. Gold Reporting should show customer 1 with two orders and `3 × 300 + 2 × 200 = 1300` cents and customer 2 with one order and 500 cents. Payment 302 does not add to item revenue. A green job does not identify correct published rows.
5. **Serving.** In the reporting pgAdmin tab or an ordinary `psql`/driver session, query the same Gold values under the reporting role. If serving cannot pin a snapshot, pause output writers, verify the latest visible Gold is the intended version before and after both reads, and use a fresh serving session with known cache behavior. When the version cannot be established, record the comparison as inconclusive. Save the ordered result/error and access evidence. A successful connection or query alone leaves freshness, storage access and permissions unverified.
6. **Replay.** After S05, run S06 using the original S04 key and payload. Verify source receipt cardinality for S04 stays one and the complete source and Bronze state still matches S05, including timestamps. At the same logical checkpoint Gold keeps customer 1 at two orders and 1600 cents and customer 2 at one order and 500 cents. New attempts or movement of unrelated WAL do not imply new business effects.

For the Phase 6 continuation, use a separately specified synthetic batch and recorded client key. Trace request ID in the request DB through its Windmill job/attempt and immutable object key/version in the operational bucket. Compute the recorded checksum from retrieved bytes, then check exact batch keys/values and approvals. With the source stopped, the request and prepared artifact can persist while still awaiting commit. On restore, verify business rows and a matching unique receipt per batch in the same source transaction, then reconcile request status. Trace those source keys through ordinary CDC into a pinned Bronze snapshot. The S04 fixture receipt and the Phase 6 write-back receipts protect different operations; S06 supplies the replay pattern, and Phase 6 must demonstrate it independently.

## Browser investigation

Start with the run ID and the evidence table. Open separate pgAdmin Query Tool tabs for the source, DuckPipe/catalog, serving service and request store as those roles become available. Label the connections by role and use read-only inspection credentials. Reuse the run's saved queries and export small result grids. Open the Windmill Runs page by job ID for logs, failed steps and retries. Use the local object-store browser (e.g. the SeaweedFS Filer view for the pinned candidate) for object discovery, then the S3 API with the tested identity for permissions, metadata and checksum evidence. Keep any administrative view confined to the disposable lab. [pgAdmin Query Tool](https://www.pgadmin.org/docs/pgadmin4/latest/query_tool.html) · [Windmill Runs](https://www.windmill.dev/docs/core_concepts/monitor_past_and_future_runs) · [SeaweedFS 4.55 Filer UI](https://github.com/seaweedfs/seaweedfs/blob/4.55/weed/server/filer_ui/filer.html)

Run independent DuckDB queries in a separate client and link their saved SQL and output from the trace table, even when the other stages are browser-visible. Use scoped service logs when a field has no UI. Phase 7 should time a reviewer following the saved walkthrough and record where they needed extra help. A short runbook plus existing tools is sufficient if the reviewer can locate both traces and distinguish pending, applied, published and committed states.

## Failure injection and recovery

**Safety rules.** Use explicitly identified disposable Compose services only. Check project name, source/consumer identities, endpoints, bucket names and volume ownership before a fault. Record an exact undo command. Inject one fault at a time against a verified baseline, keep workload and duration bounded, and monitor slot WAL, free disk, retry count and worker memory. Stop generating writes and restore service when the first predeclared ceiling is reached. Set finite slot retention and measure disk separately; the PostgreSQL retention limit is evaluated at checkpoints. Never advance/drop the live slot, delete files or reset volumes as a catch-up shortcut. Test slot loss or destructive reset only in a separate disposable exercise with a documented reseed plan. [PostgreSQL 16 replication settings](https://www.postgresql.org/docs/16/runtime-config-replication.html)

**For every fault** save pre-fault state, target, exact injection/restore commands and timestamps, evidence the fault reached its intended boundary, first error/degraded state, and any last known-good result. Record whether the intended crash window was hit. After restore preserve restart/retry IDs, elapsed recovery, and the same row/snapshot/receipt checks as the baseline. Keep intermediate wrong or stale results with their version labels. Recovery passes when the declared invariants hold within budget. An unhit crash window is inconclusive for that case.

| Fault experiment | Checks during the fault and after recovery |
| --- | --- |
| Stop the consumer after a verified checkpoint, then commit the next bounded fixture steps (e.g. stop at S02 and apply S03 and S04). | Capture inactive slot, ack/retention and the last good Bronze state. Restart against the same slot and verify exact S04 parity, including item 102 absent and all three S04 rows. In a separate replay case exercise redelivery across a restart/checkpoint if the build exposes a controllable boundary. Verify unchanged logical effects and record whether redelivery was observed. |
| Abort S04, or kill a Windmill worker before output publication and retry the same input. | Aborted source changes must stay absent. Compare the last good Gold and reader-facing output during the worker fault. Capture failed and retried jobs and verify exact output with no duplicate or partial published result. Also test a deliberately failing data check: Community Pipelines document commit-then-test, so inspect the output even on a red run and fail the safe-publication gate if bad rows are served. [Windmill Pipeline edition behavior](https://www.windmill.dev/docs/core_concepts/pipelines#community-vs-enterprise) |
| Stop or isolate the reporting service, catalog and S3 individually. | Hold a known Gold version with actual referenced Parquet and use fresh clients. Capture which path failed, client errors/timeouts or verified last-good behavior, and evidence that the other roles were available for that trial. Restore each dependency and re-run exact result/permission checks. |
| Source down during request acceptance/preparation; duplicate intake, interrupted worker or unavailable/corrupt batch object. | Inspect durable request state through restart, stable request IDs, bounded retries and object identity/checksum rejection. Once the source is available, query for prohibited business changes and receipts. A prepared or invalid batch must never be acknowledged as committed. |
| Interrupt write-back before source commit and separately after commit but before request DB acknowledgement. | Verify rollback leaves neither business rows nor receipt in the first case. In the second, prove business rows plus receipt exist even while request state lags. Retry the same request/batch (also test overlapping duplicate delivery), reconcile from source receipts, and verify exactly one logical effect per intended key. Reject conflicting payloads under a reused key. Compare CDC Bronze with committed source rows and show the source does not receive another write as the lake catches up. |

## Phase-gate checklist

Use the common evidence checks above plus the applicable checks below. A negative result can conclude a research ticket and inform an ADR. Record the corresponding phase gate as unmet if its required behavior is still missing.

- [ ] **0 — Foundation.** A reviewer can map each proposed integration to the architecture, approved local scope, candidate version/edition evidence and an explicit unknown. Review this protocol against the deterministic fixture and record accepted limits in the handover.
- [x] **1 — Source.** From a disposable reset run S00–S06 and repeat the reset. Pass with zero full-row/duplicate differences at every expected checkpoint and for the second S00, proof both S05 transactions overlapped before the recorded commit order, rollback and constraint rejection leaving prior state intact, and one unchanged S04 receipt after replay. Use read-only source SQL to inspect data, effective WAL bounds and the empty publication/slot baseline. Verify the isolation preflight and record measured resource use and labeled source WAL samples. Phase 2 begins live slot and consumer checks. [Observed source-gate evidence](experiments/EXP-009-phase-1-source-gate.md)
- [ ] **2 — CDC.** Seed before remote registration. Prove initial copy plus subsequent inserts, updates, deletes and committed/aborted changes on the simplest supported sink with exact checkpoint parity. Capture source slot/LSN and consumer evidence with distinct acknowledgement and visibility observations. Stop and restart the consumer, confirm catch-up and deleted-key absence within the declared WAL/disk/time bounds. Characterize S04/S05 multi-table visibility and record which atomicity or cutoff claims the evidence supports. Identify the actual catalog format and local file or inlining state. Keep independent shared-lake attachment and S3 acceptance in Phase 3. [Proposed Phase 2 gate](../backlog/phase-2.md#29-verify-the-complete-phase-2-cdc-gate)
- [ ] **3 — Shared lake.** An independent DuckDB process matches the expected rows at the same retained snapshot before and after a new write. Observe catalog references and real S3 Parquet access through the actual reader. Verify reader recovery after a catalog or storage interruption and record attach/version and retention limitations.
- [ ] **4 — Transformations.** A Windmill worker reads the verified input from the same lake and materializes Silver, Gold Reporting and Gold ML/Analytics with zero differences against independently declared expectations. Compare the explicit Flow and Pipeline, including an external Bronze change and whether it triggers work. Inspect job attempts and versions and verify safe publication and idempotent retry at the declared cutoff.
- [ ] **5 — Serving.** From an ordinary PostgreSQL client, match independent DuckDB Gold rows at the same version. Prove both catalog and Parquet access, deny writes and protected reads under the client role, and record driver/SQL limitations. Under a declared bounded concurrent load, verify all expected results, report request count, errors, p50/p95, CPU/RAM, catalog connections and S3 activity. Verify independent serving/catalog/S3 fault and recovery behavior.
- [ ] **6 — Async and write-back.** With source unavailable, persist a deduplicated request through restart and verify its exact prepared batch and checksum in the distinct operational bucket. Test rejection/rollback cases. After source recovery, verify approved writes and one transactional source receipt per batch across replay and acknowledgement loss. Match committed rows in Bronze and verify there is no feedback loop. Completion status reconciles to source receipts for every intended batch.
- [ ] **7 — Observability.** A reviewer follows the browser/runbook workflow for an S04 source-to-Gold trace and a request-to-commit-to-Bronze trace within a predeclared time budget. They can retrieve the independent data proof and identify a deliberately stalled or failed boundary from the same run evidence.
- [ ] **8 — Integrated resilience.** Repeat the integrated baseline and applicable single-fault/replay cases from a clean start. Compare exact data and receipt results and prescribed recovery limits across runs. Record freshness/cutoff limits, resource and latency measurements, negative findings and the feasibility decision with relevant ADRs.
