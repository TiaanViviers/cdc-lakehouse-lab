# PostgreSQL 16 publisher preparation

This procedure exercises the source side of [2.2](https://github.com/TiaanViviers/cdc-lakehouse-lab/issues/39). It uses the stock PostgreSQL 16.16 profile, the Phase 1 enrollment and native pgoutput. Connector provisioning depends on the reviewed [2.1](https://github.com/TiaanViviers/cdc-lakehouse-lab/issues/38) result. Record observations in [EXP-012](experiments/EXP-012-publisher-lifecycle.md).

## Disposable runtime

Book the disconnected guest with the current runtime owner after 2.1's priority window. Stage the pinned source image, runner and this worktree on read-only media. Use a fresh project and volume, distinct credentials and the [Phase 1 startup gate](source-profile.md). Choose a lowercase alphanumeric key starting with a letter, 8–24 characters, unique to the run. Set `CDC_RUN_KEY` and `COMPOSE_PROJECT_NAME=cdc22-$CDC_RUN_KEY` before creating the bridge and enrolling the fixture. Pause scenario writers between steps. Use a 10-minute window for the independent lifecycle probe and the Phase 1 WAL, disk and OOM stop thresholds.

Record the operator, 2.2, UTC run ID, SHA, VM overlay, Compose project, bridge ID, source image and volume labels in a new ignored `artifacts/EXP-012/<UTC-run-id>/` directory. Record the fixture UUID in the project's local enrollment file. The SQL identifies `source_lab` through that UUID, database OID and cluster system identifier. The wrapper checks the selected project, pinned image, bound volume, internal network and firewall before running the SQL. The role is `publisher_<key>`, the native publication is `pub_<key>`, the persistent slot is `slot_<key>` and the native temporary slot is `snap_<key>`.

## Baseline and authentication

1. On the enrolled clone, run the [source schema regression](source-schema.md#acceptance-checks) before preparing the CDC role. Run the existing Phase 1 fixture gate from a fresh enrollment according to its [runbook](source-gate.md) if collecting the full workload evidence. Return the publisher clone to an empty fixture before this probe begins, using the existing writer and enrollment. Capture the fixture catalog and an empty publication and slot inventory.
2. From the repository root use `admin() { bash sql/cdc/source/admin.sh "$@"; }`. Capture `admin inventory` and `admin prepare` output. Record the newly created role OID from successful setup. Repeat `admin prepare` and require SQLSTATE `42710`. Compare the selected role OID and grants before and after. Keep that enrollment and role for the remaining checks.
3. With the role still `NOLOGIN`, use the source-local interactive admin session to set a unique local password via `\password publisher_<key>`. Confirm `SHOW password_encryption` returns `scram-sha-256`. Keep the password in a mode-0600 local file. Use the administrator to get `SHOW hba_file`, then back up that file in the selected source container. Prepend these records in the observed order, substituting the exact role and the approved bridge CIDR for each permitted address family. Preserve ownership and permissions when replacing the file.

   ```text
   host  source_lab   publisher_<key>  <verified-peer-CIDR>  scram-sha-256
   host  replication  publisher_<key>  all                  reject
   host  all          publisher_<key>  all                  reject
   local replication  publisher_<key>                       reject
   local all          publisher_<key>                       reject
   ```

   Inspect `admin inventory` for parse errors and rule order. Run `SELECT pg_reload_conf();` through the existing source-admin session, then `admin enable-login "$role_oid"`. Match the actual HBA line in an allow-listed authentication log record. A parsed rule or a successful reload request alone cannot establish what authenticated a connection.

4. Use the bounded [one-shot client pattern](source-profile.md#verify-from-a-peer) with the publisher role, `PGREQUIREAUTH=scram-sha-256` and its password over stdin. Verify the allowed SQL query returns the publisher, `source_lab` and a TCP client address. With the same bridge peer try a wrong password, database `postgres`, and `replication=true` physical startup. Require the expected password/authentication rejection for each, including the explicit HBA rejection for database and physical startup. Logical startup uses `replication=database` with `source_lab`. Using the unrelated fixture reader secret, verify ordinary `source_lab` SQL and require logical replication startup to fail for lack of REPLICATION. Show that the fixture reader cannot impersonate the publisher with `SET ROLE`.
5. Run `admin permission-probe` for rolled-back SQL privilege assertions. As the authenticated publisher run `SELECT * FROM fixture.<table> LIMIT 0` against each business table, then check each negative independently with `ON_ERROR_STOP` and verbose error diagnostics. Require `42501` for reading or writing either `fixture.scenario_receipts` or `fixture.installation`, updating `fixture.order_items`, altering `fixture.customers`, creating a table in `fixture`, executing `fixture.cleanup(false, NULL)` and `SET ROLE source_fixture_owner`. Capture catalog-level CONNECT, schema USAGE, SELECT, membership and the absence of database/schema CREATE alongside the actual SQL results. Avoid raw connection strings, passwords and verifier values in outputs.

PostgreSQL 16's REPLICATION attribute gives the role cluster-wide powers over slots and physical replication when permitted by HBA. Publication access has no per-role ACL, and a logical publication is a data selection mechanism. During temporary table ownership the publisher also has owner DDL and DML powers over those tables. The dedicated cluster, first-match HBA and isolated bridge keep these powers within a disposable lab. Preserve the enrollment and receipt under `source_fixture_owner`. [PG16 logical replication security](https://www.postgresql.org/docs/16/logical-replication-security.html) · [PG16 HBA rules](https://www.postgresql.org/docs/16/auth-pg-hba-conf.html)

## Native slot and publication checks

1. With zero slots and publications, run `admin ownership-probe`. Require the four expected table mappings under the publisher-owned publication and `f|f` for elevated database CREATE and fixture-owner membership after the revoke. The writer must return deleted key and quantity `911|2`, and the reader must return `901|910|912|S04|t`. The transaction rolls back. Compare inventory to the prepared-role baseline.
2. Quiesce peer clients and run `admin create-slot`. Record the returned slot name, database OID, plugin, persistence, inactivity, restart LSN and confirmed-flush LSN. Use those two recorded LSNs as `restart_at_creation` and `flush_at_creation` below. A lost creation response leaves provenance unresolved. Preserve the evidence and stop the clone in that case.
3. Run `admin reject-publication` and require `42501` for database CREATE. Compare inventory to the post-slot capture. The failed publication attempt must leave exactly the recorded persistent slot and zero publications. Attempt repeat slot creation and require the empty-inventory refusal. Try `admin drop-slot 0/1 0/1` and require the unexpected-slot refusal and unchanged inventory. Try the same cleanup with a mismatched project name and require refusal before connecting. For the SQL-side wrong-database check, stream only `guard.sql` and `drop-slot.sql` from the worktree to source-local admin psql targeting the built-in `postgres` database on this same clone, supplying the recorded variables. Require the unexpected-source error before any slot operation. Then run `admin drop-slot "$restart_at_creation" "$flush_at_creation"` against the enrolled source and confirm zero slots and publications.
4. Repeat slot creation and save its fresh fingerprint. Run `admin snapshot-slot-probe "$restart_at_creation" "$flush_at_creation"`. Require the second position to be a temporary pgoutput slot held by the same session and a third allocation to fail with `53400`. After the native session exits, require only the original inactive persistent slot. This exercises PostgreSQL capacity and temporary allocation. The connector's actual snapshot sessions must be observed in 2.1 and the final lifecycle trial.
5. Run `admin publish` and capture its publication OID, the exact four unfiltered mappings, owner and writer/reader probes. Compare the four owners, identities and fixture ACLs with the prepared baseline. Require replica identity `d` and valid primary keys. Confirm again that the publisher can read those tables and lacks business-table DML after owner restoration. Run `admin publish` a second time and verify refusal with the same existing publication OID. Run `admin drop-publication "$publication_oid"` while the slot remains and require refusal.
6. For a same-name collision after a successful slot creation, use a fresh enrolled clone and create an administrator-owned publication with the expected name over just `fixture.customers` using source-local admin psql. Record its OID and mapping. Require `admin publish` to refuse, then clean up just the recorded test slot. Even with the collision publication's real OID, `admin drop-publication` must refuse to remove it. Capture unchanged owner/OID/membership. Leave that object to the operator who created it.
7. To check active refusal, use a replication-mode peer with `pg_recvlogical --start --no-loop --status-interval=0 --file=/dev/null --option proto_version=1 --option "publication_names=$publication" --slot="$slot"` over the isolated bridge. Use `--dbname=source_lab --host=source-db --username="$publisher" --no-password` and the same secret-input pattern as psql. Bound the peer with an external deadline and check for `active=t` before running `admin drop-slot` with the creation fingerprint. Require the active-slot refusal and unchanged identity. Stop that exact peer and require `active=f`. Use a separate fresh clone for this case if repeatability is affected by receiver feedback. A changed fingerprint blocks the native drop. Preserve that volume for inspection or tear down the documented disposable clone.
8. With the peer stopped, disable login using `admin disable-login "$role_oid"`. Check no publisher sessions remain before dropping the native slot and publication in that order. Hold exclusive use throughout. Verify zero slots and publications. Restore the backed-up HBA file, reload and verify the original rules, then run `admin drop-role "$role_oid"`. Compare catalogs and fixture ACLs with the untouched baseline and run the regression before a retained volume is reused. If a guard fails, retain the inventory and identify the owning experiment.

The native cleanup matches an unchanged slot fingerprint recorded during controlled creation and a publication OID/owner/definition. PostgreSQL 16 has no slot owner or immutable slot ID. Two uncoordinated sessions can replace a slot between a catalog check and a drop. Exclusive access, upfront collision checks and quiescence are required. The server's SQL drop also refuses an active slot at acquisition. Connector-driven LSN advancement and object cleanup require a reviewed identity contract.
