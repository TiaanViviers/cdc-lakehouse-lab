# Phase 3 shared-lake research strategy

**Planning proposal · 2026-11-27.** Phase 3 aims to demonstrate that a separate DuckDB process can read exact current and retained values through the actual DuckPipe-created catalog and its S3 Parquet data. This is a compatibility and recovery experiment under held, verified source checkpoints. Upstream source inspection identifies the interfaces below. End-to-end interoperability is open. [M3 requirements](poc-specification.md#phase-by-phase-exit-gates) · [Draft backlog](../backlog/phase-3.md)

## Prove the actual writer path early

1. **Provision bounded S3 storage.** Start with the documented 4.55 all-in-one `weed server` candidate using `-s3`, an explicit `-s3.config`, `-s3.port=8333`, a persistent directory including filer metadata and volume data, capped volume count and size, and `-master.telemetry=false`. Confirm actual command flags, state paths, health, resolved budgets and administrative port reachability before starting writer tests. Stage local identities for bootstrap, ingestion and read-only access. Test path-style SigV4, List/HEAD, ranged GET, successful multipart completion and bounded abort, wrong/anonymous credentials and cross-bucket denial. Use a tiny separate synthetic probe bucket to validate S3 I/O. Disable optional endpoints and constrain access to filer/master/volume ports to prevent bypass of the gateway's authorization. Use TLS when the pinned clients can be configured with a trusted local CA. A signed HTTP control, if needed, belongs only inside the disconnected disposal boundary with ephemeral credentials and documented transport settings. [Tagged server flags](https://github.com/seaweedfs/seaweedfs/blob/4.55/weed/command/server.go) · [Gateway entrypoint](https://github.com/seaweedfs/seaweedfs/blob/4.55/docker/entrypoint.sh)
2. **Use a fresh consumer-owned catalog.** The pinned PostgreSQL extension initializes `ducklake` with a local data root. `duckpipe.add_table` issues PG `CREATE TABLE ... USING ducklake`. The DDL hook propagates `ducklake.default_table_path` to the embedded engine, whose custom base path is used when creating the table. First test setting that GUC in the registration session to `s3://<lake-bucket>/<run-prefix>/` before a new mapping is created. Verify the catalog records the effective table path and path mode and that later worker connections resolve it. The stored catalog root may remain local. For M3, every accepted Bronze table and covered version must resolve required data/delete files to S3 with no reader access to the writer filesystem. Compare a supported whole-lake S3 root only on a fresh disposable catalog if necessary. Direct writes to DuckLake metadata, path overrides that mask the recorded path and Bronze data written by a second engine are outside acceptance. [Registration](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-pg/src/api.rs#L978-L999) · [Pinned initializer](https://github.com/relytcloud/pg_ducklake/blob/20d799e673639fb0c36a3b31db413e45057a10ed/src/pgducklake_duckdb.cpp#L74-L102) · [Path setting](https://github.com/relytcloud/pg_ducklake/blob/20d799e673639fb0c36a3b31db413e45057a10ed/docs/settings.md) · [Table path resolution](https://github.com/relytcloud/pg_ducklake/blob/20d799e673639fb0c36a3b31db413e45057a10ed/third_party/ducklake/src/storage/ducklake_schema_entry.cpp#L80-L106)
3. **Exercise real CDC worker sessions.** The PG group worker reads pg_duckdb FDW servers and user mappings at startup. The snapshot and per-table flush code both open DuckDB, attach the PostgreSQL DuckLake catalog and then inject generated `CREATE SECRET` statements. Its secret failures are logged and can be nonfatal. Provision a scoped S3 FDW server and current-worker mapping with the exact build's supported region, endpoint, path style, scope and HTTP/TLS options. Verify the session role, effective options, lack of AWS fallback, actual request identity and credential refresh on restart. Test the worker path as well as the separate native session used for scoped materialization. For a nondefault endpoint, verify the generic FDW option path against the installed build; the simple SQL helper signature alone does not establish support for every transport option. Validate negative auth and redaction. [Worker startup](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-pg/src/worker.rs#L250-L279) · [FDW secret query](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-core/src/duckdb_secrets.rs) · [Engine initialization](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-core/src/duckdb_flush.rs#L57-L104)
4. **Force a physical path and keep an inline control.** Use the supported table-level `data_inlining_row_limit` option and inspect effective catalog settings after registration. DuckPipe can update the global option when configured with a positive limit. A zero DuckPipe GUC alone leaves the actual DuckLake default to the embedded path. Materialize already-inlined rows via the supported table-scoped `ducklake.flush_inlined_data` under a hold when needed. For the object-backed apply proof, use current-state insert/update/delete from the source and require catalog references that trace to DuckPipe-originated rows. Exercise DML over an already file-backed checkpoint. Capture data and delete refs or the supported rewrite that replaces them, and retain a control with a real scoped delete-file path where supported. Record the commit and materialization snapshots independently. A successful flush or an S3 object listing alone leaves parity and transaction completeness unverified. [Pinned option and flush APIs](https://github.com/relytcloud/pg_ducklake/blob/20d799e673639fb0c36a3b31db413e45057a10ed/sql/pg_ducklake--0.1.0.sql#L156-L221) · [Pinned inlining implementation](https://github.com/relytcloud/pg_ducklake/blob/20d799e673639fb0c36a3b31db413e45057a10ed/third_party/ducklake/src/functions/ducklake_flush_inlined_data.cpp)

## Attach once, read one retained version across all tables

Use the same consumer cluster, database and `ducklake` metadata schema with an independent process and provisioned SELECT-only catalog access. Network HBA is first-match SCRAM for the reader's catalog principal and exact peers. Grants must cover the actual format's metadata and any required inline tables while denying writes, schema creation, DuckPipe configuration and access to protected namespaces. Pin the catalogs and storage independently. PostgreSQL access certifies neither possession of the S3 objects nor authorization to read them. The S3 reader uses read/list on the designated bucket scope, with no upload/delete capability. Send secrets through protected local inputs and keep them out of SQL traces and review artifacts. [Pinned reader/catalog form](https://ducklake.select/docs/0.4/duckdb/usage/connecting)

The 0.4 syntax candidate uses a placeholder DSN provided via a protected channel. Confirm successful offline loading and exact catalog identity before the first read.

```sql
LOAD postgres_scanner;
LOAD ducklake;
LOAD httpfs;
ATTACH 'ducklake:postgres:<catalog-dsn>' AS bronze_lake (
    METADATA_SCHEMA 'ducklake',
    READ_ONLY,
    CREATE_IF_NOT_EXISTS false,
    AUTOMATIC_MIGRATION false
);
SELECT * FROM bronze_lake.snapshots();
SELECT item_id, order_id, quantity, unit_cents
FROM bronze_lake.bronze.order_items AT (VERSION => 14)
ORDER BY item_id;
```

Version 14 illustrates syntax using a local EXP-019 result. A Phase 3 run chooses its own observed ID and uses that same ID for every business projection and report. Verify schema, table, snapshot and storage path identity before and after use. Resolve the data and delete files by catalog IDs, version validity intervals, schema/table paths and relative flags; join deletes to the corresponding data file and account for retained versions and inlined segments. Use bounded inspections, object HEAD and size/digest evidence, Parquet footer checks and observable GET/Range or the authorization-loss control. Loose Parquet rows and position deletes are physical evidence. Exact keyed DuckLake results establish the logical effects of updates and deletes. [DuckLake 0.4 time travel](https://ducklake.select/docs/0.4/duckdb/usage/time_travel) · [Pinned file metadata](https://github.com/relytcloud/pg_ducklake/blob/20d799e673639fb0c36a3b31db413e45057a10ed/third_party/ducklake/src/storage/ducklake_metadata_manager.cpp#L195-L218)

Repeat the retained read in a fresh process after later CDC changes. While the selected version is retained, deny only S3 access and require a file-backed read to fail while an appropriate inline control can still read. Restore access and require exact recovery. Independently deny catalog access, require a fresh attach to fail, then restore and recheck. Replace the relevant containers with matched named volumes and compare IDs, references and exact data. Test a bounded writer interruption while storage is unavailable. Confirm an affected checkpoint cannot be declared exact or feed downstream publication, inspect ack/headroom and catalog/orphan behavior, restore access, and require exact caught-up data or record the failure. Establish separate time and size bounds for any orphan or multipart inventory. Never remove paths based on listing alone. For historical acceptance, keep automatic expiry and external bucket lifecycle deletion from invalidating a retained input. Restore metadata and data as a matched cut in any later recovery drill.

## Catalog separation, retention and later clients

The core coordinator has a `ducklake_catalog_connstr` override. In extension mode, registration and control paths still operate on the consumer PostgreSQL relation and its local metadata, and the installed native extension attaches its own catalog. The override proves a connection configuration exists; bootstrap, native relation identity, DDL, resync, checkpoints and recovery across two catalogs remain unverified. Keep colocation for M3 and R08 open. Explore separation only against disposable copies with single-catalog identity checks across every control and write path. Managed RDS would be a metadata-host candidate subject to verification. [Catalog resolution](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-core/src/flush_coordinator.rs#L382-L409) · [Native catalog setup](https://github.com/relytcloud/pg_ducklake/blob/20d799e673639fb0c36a3b31db413e45057a10ed/src/pgducklake_duckdb.cpp#L74-L102)

Windmill's native runner candidate is a different DuckDB generation and standalone pg_ducklake v1.0.3 expects format 1.0. Passing the 1.5.1 reader test certifies that reader only. Carry forward a pinned worker-process reader option and compare a jointly tested writer/worker/serving upgrade under separate review. Cross-writer metadata commits, conflict handling and ownership need their own evidence. Migration and relocation are distinct, as are catalog backup and object preservation. A migration experiment needs a disposable, matched catalog and storage clone, a verified restore path, versioned parity and restart on the chosen writer/reader set. Changing the active catalog version or path needs explicit authorization and compatibility evidence before cutover.
