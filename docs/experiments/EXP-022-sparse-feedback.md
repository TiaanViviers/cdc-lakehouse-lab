## Hypothesis and procedure

If the pinned group checkpoint is an oldest-table watermark, an idle mapped customer table can hold feedback stationary while the three other table queues commit their work. Repeat the original paired subgate on current main, then extend the same pin with the [sparse and crash schedule](../../tests/integration/cdc-sparse/README.md). Predeclare the duration, transactions, resource stops, parity and restart criterion before staging any run. Seed and register serially while source writes are held. A successful correction must move acknowledgement over a committed prefix and remain within the storage budget without requiring a customer row change.

The guest used the reviewed 2-vCPU and 2-GiB envelope, internal dual-stack bridge with both firewall families, and distinct named volumes for source and consumer. The bootstrap applied one DuckDB thread, 16 MiB buffer memory, 96 MiB flush memory, a single concurrent flush and a 1 MiB queue byte threshold. The stock trial used the default five-second flush interval. The fault repeat overrides only this setting in its fresh consumer. Use `sha256sum -c SHA256SUMS` on the staged media and the bounded run commands in the reproduction procedure.

## Correctness invariant and candidate review

For a stable publication and mapping generation, at every persisted or advertised frontier **F**, all eligible effects of each source transaction with END at or below **F** must already be durable, be covered by a proved snapshot boundary, or be reconstructible from a durable replay log with sufficient ordering and identity to recover the same state. Resume may request at most that frontier. Outstanding work includes work still in routing and wire buffers, in per-table queues, in worker-local batches, in uncommitted sink transactions, and failed or skipped work whose coverage is unresolved. A mapping state, idle timeout, maximum row-message LSN, or empty visible queue provides no absence proof.

| Option | Finding |
| --- | --- |
| Tune poll, flush or batch settings | Can change latency, batching and backpressure. The minimum calculation still includes idle mappings. No supported feedback override was found in the pinned [configuration documentation](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/doc/USAGE.md#configuration). |
| Separate groups/slots | Isolates a slow table's apply path. An idle group still owns a slot in the same cluster. Publisher retention is constrained by the oldest required restart point. More slots also exceed the stock two-slot lab allowance once snapshot slots are needed. |
| Touch all tables on a schedule | EXP-018 moved the minimum to the next table position and subsequent sparse activity stalled again. A recurring touch depends on continuously present writable rows, real overhead and triggering/locking consequences. A touch cannot attest dispatch of earlier failed work. An additional published heartbeat table by itself cannot lift the older minimum. |
| Throttle or halt writes at a WAL budget | A useful containment control for this disposable experiment. A retention guarantee requires a bound on all WAL in the cluster, including unrelated transactions and maintenance, and a way to resume without renewed growth. This pin has no such feedback recovery mechanism. |
| Larger slot cap, manual advance, invalidation or resnapshot | Rejected for normal operation. EXP-018 tests invalidation and loss recovery as a separate failure boundary. |
| Max of active table LSNs, ignoring idle mappings, or raw receive watermark | Rejected. A fast table may be durable while another still has earlier uncommitted sink work. An LSN reported by PostgreSQL as produced or sent is independent of local sink durability. The existing drain helper discards the timeout outcome and cannot certify success. |
| Proof of a committed stream prefix | Preferred design for review. Make dispatch fail closed, use a generation-scoped ordered token for every eligible effect, and seal a prefix at COMMIT END. A worker supplies contiguous durable completion tokens after sink commit. Publish only a prefix covered by every touched mapping. An idle mapping needs only a positive absence proof from decoding the sealed prefix. Use bounded tracking and backpressure without blocking the delivery of the current transaction boundary. Even with correct acknowledgement, a long-running source transaction can hold restart WAL and a stalled sink can halt progress. The proposed guarantee applies to workloads with bounded source transactions and enough sink throughput to absorb ongoing work. |

As a counterexample, suppose T1 updates an order and deletes an item. The order writer commits while the item writer has only moved its delete to a local buffer. T2's order-only update can also commit before the item-side delete commits. The maximum order position can then point beyond T1's END even if a shared queue appeared empty. A crash at that point leaves the item present, and a resume after T1 cannot replay the delete. A later item flush also cannot raise the frontier if the delete was discarded on error. The completion proof needs both transaction closure and an unbroken path from admission to durable effects.

A first candidate can use a fence that stops admission at a completed transaction and waits for every admitted operation to return a durable completion token. A temporary scoped transactional logical marker could force a decoded BEGIN/COMMIT during silence for this proof. PG16.16 can emit a transaction containing only that marker with `messages 'true'`. It would still need bounded cadence and WAL cost, and verified delivery of the resulting COMMIT. A later version could use the pinned sender keepalive under the stronger ordered receive proof. A timeout, missing or errored token, unsupported message, queue generation change or routing gap must hold the previous frontier. A commit record for the proven group frontier must survive restart before publication. Atomic per-mapping apply receipts or replay-safe effects are required if a crash can leave partial application beyond the group frontier. Reconnection must discard generation-local evidence and validate persisted progress. [Transactional logical message source](https://github.com/postgres/postgres/blob/REL_16_16/src/backend/replication/pgoutput/pgoutput.c#L1677)

Regression cases for that candidate include a fast table beyond a stalled table, a dormant mapping becoming active mid-transaction, a cut between rows and COMMIT, a worker draining work before it becomes durable, a failed flush followed by a successful flush, failed checkpoint persistence, skipped or misrouted work, and an old generation delivering a late completion. Crash immediately before and after sink commit, after durable frontier persistence but before sender feedback, and after observed feedback. Require exact keyed state after restarting the same slot with a transaction containing both a real delete and update, including failure and replay of the effects around that boundary. Test filtered/nonpublication WAL and a fully silent interval. Coordinate generation and routing changes with 2.12 before review.
