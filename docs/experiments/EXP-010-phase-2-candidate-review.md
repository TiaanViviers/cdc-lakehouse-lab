## Hypothesis

The pinned pg_duckpipe extension in its own PostgreSQL process can log in to stock PG16.16 over local Docker TCP with SCRAM, seed a DuckLake table from committed rows and correctly reflect one committed insert, update and delete. The consumer is expected to form a PostgreSQL-backed DuckLake **0.4** catalog with local table data. An exact one-table result is the first decision gate. Sustained replication, restart and cross-table behavior require separate tests.

## Interpretation

The wire protocol makes PG16 a credible remote source. The maintenance DDL, temporary-slot pressure and untested remote DML make a standalone smoke result the earliest useful commitment point. A successful experiment must pass the same row assertions over TCP that are missing from the upstream loopback test. Confirm actual storage format as part of selecting the candidate, so downstream clients can plan from the writer the lab actually ran.

## Limitations / confounders

Registry records and code establish provenance and intent. No candidate image was booted and no remote session, extension load, catalog inspection, ack or row apply occurred in 1.9. A smoke failure could reflect offline packaging, permissions, slot capacity, authentication, protocol, snapshot filtering or the target apply hook. Isolate the failing stage before changing one dimension. A stale-image rebuild can change the PostgreSQL package, bundled dependencies and code generation. Record exact build inputs and avoid attributing a result to one change without a controlled comparison.
