## Pinned behavior and attribution

**Verified source and documentation, checked 2026-11-27.** Remote `create_group` creates the persistent pgoutput slot and publication. Registration adds the relation to the publication and creates a local mapping. The group worker requests `START_REPLICATION` from the persisted group position, and PostgreSQL uses the greater of the requested LSN and the slot's confirmed position. Independently, each snapshot starts a SQL repeatable-read transaction on the copy-control connection. Its first query creates a temporary logical slot and receives the decoding consistent point. That SQL transaction supplies the row view for COPY. The SQL function initializes logical decoding but does not import a replication-protocol snapshot into the read transaction. COPY closes its connection and releases the temporary slot. [Pinned API](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-pg/src/api.rs) · [Pinned COPY](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-core/src/snapshot.rs) · [PG16 replication start and slot options](https://www.postgresql.org/docs/16/protocol-replication.html) · [PG16.16 SQL slot creation](https://github.com/postgres/postgres/blob/REL_16_16/src/backend/replication/slotfuncs.c) · [PG16 repeatable read](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-REPEATABLE-READ)

The receiver turns pgoutput BEGIN and COMMIT into decoder messages and passes raw `XLogData.wal_start` with DML. In protocol 1, the BEGIN contains the XID and final LSN of the already committed transaction. COMMIT has the commit record LSN and transaction end LSN. A relation message populates the relation cache. DML resolves mapping by source name, then OID as fallback, and lazily creates the mapping's flush queue. In SNAPSHOT it buffers DML in a paused queue. Successful COPY updates the mapping to CATCHUP with the consistent point, unpauses any existing queue and invalidates the cached mapping before later dispatch. A row first delivered in CATCHUP reaches a different path. Stock `should_skip_change` rejects that row if its transport LSN is at or below the snapshot LSN. COMMIT still advances pending progress to the end LSN, which permits CATCHUP to become STREAMING. Neither that state change nor an empty queue proves admission or durable apply of the row. The STREAMING append replay rule is a separate comparison against per-change applied LSN. [Pinned receiver](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-core/src/slot_consumer.rs) · [Pinned service](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-core/src/service.rs) · [Pinned coordinator](https://github.com/relytcloud/pg_duckpipe/blob/86d5c248d80370fb2e10ddc1abd780fd94c3a52b/duckpipe-core/src/flush_coordinator.rs) · [PG16 logical message fields](https://www.postgresql.org/docs/16/protocol-logicalrep-message-formats.html)

## Candidate decision and provenance

Carry BEGIN's XID and final LSN across poll cycles on the current persistent connection. For DML in CATCHUP with an established point, reject only a transaction whose final LSN precedes that point. A commit record can start at the point, and a transaction may write a row before the point and commit later. Missing BEGIN in CATCHUP raises a stream error and uses the existing reconnect path. Keep raw row LSNs for change storage and the existing append replay rule. This patch makes no changes to feedback, checkpoint SQL or production configuration. The code includes three tests for row/commit boundary equality, early-row late-commit behavior, missing BEGIN, paused admission and streaming replay.

## Limitations and handoff

**Second observed blocker, guest 49.** An assigned fixture writer XID held the slot initialization wait. The source inserted and committed exact S01 while that backend initialized the temporary slot. The persistent sender remained suspended until mapping 4 reached CATCHUP. The read view `747:750:747` excludes the writer XID 747. COPY wrote two rows. The row began at `0/19A8F98`, committed at `0/19A90B0` and ended at `0/19A90E0`, all before the returned consistent point `0/19A9118`. The fixed rule still logged `skip=true`. The source read was exact and the target missed item 102 at the deadline. The slot-initialization failure reproduced the risk that the SQL read view and logical decoding point represent different source boundaries. A commit-LSN comparison alone cannot distinguish such a transaction from one already represented in COPY. [PG16.16 logical snapshot builder](https://github.com/postgres/postgres/blob/REL_16_16/src/backend/replication/logical/snapbuild.c)

**Open correction.** Use a proven snapshot/decoding pairing or retain evidence of exact source transaction visibility through routing and replay. The PostgreSQL replication protocol can export or use the slot's own snapshot. Integrating that path would require a compatible logical replication connection, queue handling for already-buffered pre-boundary changes, and restart coverage. The pinned connector's SQL slot creation supplies a separate read view. No aligned implementation was run. Append-mode COPY, DDL/TRUNCATE and crash/reconnect during COPY also remain open. Neither observed miss establishes permanent loss after a reconnect, and the experiment preserved the failure for review without a reseed or Bronze repair. [PG16 slot snapshot options](https://www.postgresql.org/docs/16/protocol-replication.html)

The candidate is an opt-in library over the published consumer image. The integration owner can replay the series, or reconcile the routing change with future feedback work, and then run the full [2.13 / #61 gate](https://github.com/TiaanViviers/cdc-lakehouse-lab/issues/61) on reviewed common artifacts. 2.11 owns the committed-prefix feedback investigation and its sparse result remains negative. This report supplies the reversible partial correction and the unresolved slot-initialization blocker for the integration decision. Neither the candidate nor M2 is ready for acceptance.
